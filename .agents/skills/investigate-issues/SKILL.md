# Issue並列調査

複数Issueの着手判断に必要な評価を、Issueごとに独立した調査として並列化し、同一形式で比較可能にする手順。手順の正典は本ファイルであり、オーケストレーションを許す枠組みはG-0010(決定1・2)にある。

## 入力

- Issue番号列(1〜8件)。9件以上を渡された場合は先頭8件だけを調査し、**残りを調査対象外として明示的に報告する**(無言で切り捨てない)。
- 番号が不明な場合は、先に`gh issue list`で候補を確定してから使う。

## 各Issueの調査内容(同一形式)

Issueごとに、次を**この見出し構成のまま**出す。根拠には参照したファイル・ADR・Issue番号を挙げる。

1. **規模**: S(1日以内)/ M(数日)/ L(スライス級)と、その根拠。
2. **依存**: 先に解決すべきIssue、前提のADR、影響し合うコード領域。
3. **ADR要否**: 新しい設計判断を含むか。含むなら論点を1行で。
4. **CI検証可能範囲**: `just check`で守れる部分。
5. **実機限定範囲**: TCC・実ハードウェアでしか確認できない部分(docs/domain-pitfalls.md #8)。無ければ「なし」。
6. **PR分割案**: 1 Issue = 1 PRで収まるか、分割するなら境界。
7. **リスク・未知**: 調査で解消できなかった不確実性。

調査で読む対象: Issue本文とコメント、関連ADR、`docs/domain-pitfalls.md`、`docs/plan/IMPLEMENTATION_PLAN.md`(スライス関連の場合)、言及されているコード。**コードを変更しない読み取り専用の調査**とする。

## 統合

全Issueの調査後、依存関係を考慮した**推奨着手順**と理由を1つにまとめる。個別調査と矛盾する場合は個別調査を修正せず、矛盾を明記する。

## オーケストレーション(G-0010 決定1・2)

- **目的**: Issueごとに独立した調査を並列化し、比較表の作成を1ターンで終える。
- **エージェント数の上限**: 1回の起動で最大9体(Issueあたり調査1体 + 統合1体)。
- **停止条件**: 各Issueの調査は1回で打ち切る。失敗・タイムアウトしたIssueは「調査失敗」として結果に含め、再試行しない。統合も1回。
- Workflow機構を持つAgentは、製品別アダプター側のスクリプト(Claude Codeは`.claude/workflows/investigate-issues.js`)で起動する。
- **Workflow機構を持たないAgent(codex / github-copilot / 未登録のfallback)は、同じ調査内容を逐次実行し、同一の出力形式を満たす。**

## 結果の扱い

1. 恒久的に残す価値のある判明事実(規模の根拠、依存の発見)は、対象IssueへのコメントとしてGitHubに書く(AGENTS.md「知識の置き場所」)。
2. 比較表と推奨着手順は`report-queue`スキルに従いP2で1件として積み、1ターン1件で報告する。調査中に発見した緊急事項(既知の障害の再発など)だけはP1の別件にする。
3. 本スキルは判断材料を作るまでとする。**着手判断・計画承認は利用者が行い、`plan-execute-verify`の手順を置き換えない。**
