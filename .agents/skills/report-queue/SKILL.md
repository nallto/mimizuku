# 報告キュー

利用者が一度に捌ける量を超える報告を防ぎ、セッションが切れても報告待ちを引き継ぐための手順。手順の正典は本ファイルであり、そうする理由はG-0010にある。

## いつ使うか

- 並列実行(Workflow・サブエージェント)で複数の結果が同時に返ったとき。
- 無人実行や定期巡回で、利用者が見ていない間に結果が出たとき。
- セッション開始時に、前のセッションからの報告待ちがあるかを確認するとき。

## 1. 恒久的な知識を先に書く

キューへ積む前に、残すべき知識をその置き場所へ書く(AGENTS.md「知識の置き場所」)。調査結果と判明した事実はIssueコメント、設計判断はADR、ドメインの罠は`docs/domain-pitfalls.md`。**キューには報告待ちの通知だけを置く。** キューを失っても知識が失われない状態を保つ。

## 2. キューへ積む

`local/agent-artifacts/report-queue/`へ、1件1ファイルで置く。**パスはメインチェックアウトのルート基準で解決する** ―― worktree内で作業している場合も、`git rev-parse --path-format=absolute --git-common-dir`の親をルートとして使う。worktreeは撤収で消えるため、その中へ積むと報告待ちが失われる。

ファイル名は`<YYYYMMDD-HHMMSS>-<slug>-<4桁の乱数>.md`とする。優先度をファイル名へ入れない(優先度の正典はfrontmatterで、変更時にリネームが必要になる多重管理を避ける)。乱数接尾辞は、並行セッションが同時刻・同slugで衝突しないためのもの。

ファイル名の時刻と`created`は、**同一の実クロック読取に由来させ、同一秒を指す**ようにする。LLMは現在時刻を知らないため、文脈からの推定で時刻を書くことを禁止し、必ず`date`コマンドの実行結果を使う。秒境界を跨がないよう、1回の`date`実行から両方の書式を得る。

```bash
read -r ts created <<<"$(date '+%Y%m%d-%H%M%S %Y-%m-%dT%H:%M:%S%z')"
# ファイル名: ${ts}-<slug>-<4桁の乱数>.md / frontmatter: created: ${created}
```

実クロックを取得できないAgent(shell実行不可など)は、キュー項目を**新規作成しない**。その報告はセッションの通常報告で行う(推定時刻の項目がキューへ入ると報告順の正典が壊れるため。fail-closed)。この規則はキューが`local/`配下でCIから見えず(G-0009)、強制点をAgent実行時にしか置けないため、機械強制ではなく手順として定める。

```markdown
---
priority: P1 | P2 | P3
created: 2026-08-17T09:30:15+0900
source: <生成した作業。Issue番号、PR番号、巡回名>
related: <Issue / PR / ファイルへの参照>
status: pending
---

<3行以内の要点。詳細はrelatedの参照先に書いてあること>
```

項目を更新したときは、`date`実行で取得した時刻を`updated`(任意フィールド)としてfrontmatterへ記録する。`created`は作成後に変更しない。既存項目の分精度の`created`(秒なし)はそのまま有効で、訂正不要(辞書順比較で同時刻の秒付きより前に並ぶだけで、順序の正しさは保たれる)。

優先度は判断で決めず、次の規則で決める。

| 優先度 | 対象 |
| --- | --- |
| P1 | `main`が壊れている / `main`のCIがred / データ喪失につながる不具合の発見 / 無人作業が承認を要する地点で停止した |
| P2 | 着手判断を待っている / 実機検証待ちのdraft PRができた / 作業中PRのCIがredで判断が要る |
| P3 | 情報提供のみ(調査結果、提案、影響のない気づき) |

判断に迷う場合は低い方へ置く。P1を増やすと1ターン1件の意味が薄れる。

## 3. 報告する

1. `status: pending`のうち最優先(同順位なら`created`が古いもの、`created`も同値ならファイル名の辞書順が先のもの)を**1件だけ**報告する。
2. 末尾に残件を1行で添える(例: `残 3 件(P2:2, P3:1)`)。全件の要約を並べない。
3. 報告したファイルは削除する。利用者の判断待ちで参照が続く場合は、報告する**前に**`status: reported`へ更新してから報告し(報告直後にセッションが落ちても二重報告にならない。この更新でも`updated`を`date`実行で記録する)、判断が済んだ時点で報告した側が削除する。`status: reported`のまま次のセッションへ持ち越したものは、冒頭で判断が済んだか確認し、済んでいれば削除する。
4. 利用者が「次」と求めたら次の1件を報告する。求められていないのに連続で出さない。
5. セッション開始時にpendingがあれば、最優先の1件だけを提示する。

P1は例外として、待たずに即時報告する。ただし1ターン1件は守り、他のP1があれば残件行で件数を示す。

## 4. 後始末

キューは一時物であり、`local/`はgit管理外(G-0009)。空になったディレクトリは残してよい。恒久化すべき内容がキューにしか無い状態でファイルを削除しない。
