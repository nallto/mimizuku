# スライス着手前の下調べ

スライス(または大きめのIssue)へ着手する前に読むべき正典を並列に読み、計画の材料を1つにまとめる手順。手順の正典は本ファイルであり、オーケストレーションを許す枠組みはG-0010(決定1・2)にある。

本スキルは`plan-execute-verify`の**計画段階の入力を作るもの**であり、計画そのものの提示・承認手順を置き換えない。出力は草案であって、承認を得る計画は利用者との対話で確定する。

## 入力

スライス番号(例: S7)またはIssue番号を1件。対応関係が不明なら、先に`docs/plan/IMPLEMENTATION_PLAN.md`とGitHub Issueで確定してから使う。

## 読むソース(5つ固定)

それぞれ独立に読み、事実・制約・未決論点を報告する。

1. **実装計画とIssue**: `docs/plan/IMPLEMENTATION_PLAN.md`の該当スライス、対応Issueの本文とコメント。受け入れ条件、依存スライス、明記済みの申し送り。
2. **関連ADR**: `docs/adr/`から該当スライスに効く決定を洗い出す。決定済みで変えられない制約と、そのスライスで起票が予定されている判断(D番号)。
3. **デザイン正典**: `docs/DESIGN.md`と`docs/design/`の対象画面・操作仕様。UIに触れないスライスでは「該当なし」を確認して終える。
4. **ドメインの罠**: `docs/domain-pitfalls.md`から該当する罠を列挙する。再発見しない(AGENTS.md)。
5. **既存コード**: 触ることになる領域の現状(責務境界、既存テスト、`Packages/*`とAppの分担)。読み取り専用。

## 出力形式(統合)

次の見出し構成のまま1つにまとめる。根拠には参照したファイル・ADR・Issue番号を挙げる。

1. **計画草案**: 対象・手順・検証方法・トレードオフの素案(`plan-execute-verify`の計画に要求される粒度)。
2. **未決論点**: 実装前に決める必要があるもの。ADR起票が要る判断はその旨を明記。
3. **実機検証項目**: TCC・実ハードウェアでしか確認できない項目(docs/domain-pitfalls.md #8)。
4. **CI検証可能範囲**: `just check`で守れる部分と、そのためにCoreへ置くべき純ロジック。
5. **PR分割案**: 1 Issue = 1 PRで収まるか、分割するなら境界(G-0003)。
6. **未読・不確実性**: 読めなかったソース、調査で解消できなかった未知。

## オーケストレーション(G-0010 決定1・2)

- **目的**: 正典5ソースの読み込みを並列化し、計画材料の作成を1ターンで終える。
- **エージェント数の上限**: 1回の起動で最大6体(ソースあたり読み手1体 + 統合1体)。
- **停止条件**: 各読み手・統合は1回で打ち切り、再試行しない。読めなかったソースは「未読」として結果に明示し、読んだことにしない。
- Workflow機構を持つAgentは、製品別アダプター側のスクリプト(Claude Codeは`.claude/workflows/slice-prep.js`)で起動する。**Workflow機構を持たないAgent(codex / github-copilot / 未登録のfallback)は、同じ5ソースを逐次に読み、同一の出力形式を満たす。**

## 結果の扱い

1. 恒久的に残す価値のある判明事実は対象Issueへのコメントとして書く(AGENTS.md「知識の置き場所」)。
2. 統合結果は`report-queue`スキルに従いP2で1件として積み、1ターン1件で報告する。
3. 着手判断・計画承認は利用者が行う。本スキルの出力を「承認済み計画」として扱わない。
