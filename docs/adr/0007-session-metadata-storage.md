# ADR-0007: セッションの正典はJSONスナップショット、処理中はJSONLジャーナルにする

- ステータス: Accepted
- 日付: 2026-07-29
- 関連: #29(判断 D2) / #38(S5) / #43(S10) / #32(D5) / ADR-0006

## Context(背景)

S5では、録音と同じセッションディレクトリへ、タイトル・開始日時・長さ・タグ・ステータス・ストリーム開始オフセットなどのメタデータと、確定した文字起こしを保存する。録音中の異常終了でも、失ってよいのはまだ確定していない現在の発話だけであり、確定済みの内容と既存メタデータを壊してはならない。保存データはオンデバイスに留め、将来の一覧・フィルタ・全文検索、外部ツールでの利用、スキーマ変更にも対応する必要がある。

Speechの結果が区切る`TranscriptSegment`は認識器の改訂単位であり、利用者が読む段落の単位とは限らない。同じ話者ラベルが不自然に細切れになるため、ライブ表示では到着した結果をそのまま使えても、停止後には句読点・無音区間・ストリーム切替などを基に表示ブロックを組み直せる必要がある。また、正常停止では入力を閉じた後にSpeechのfinalizeを待ち、最後のvolatile結果を可能な限り確定させてから保存する必要がある。

S18とS19では、既存録音の再文字起こしと、外部の動画・音声ファイルのインポートを行う。これらもライブ録音と同じく「認識中の追記」「入力終端でのfinalize」「表示用の整形」「既存文字起こしとの安全な差し替え」を扱えなければならない。外部音声はマイクまたはシステム音声とは限らず、複数話者が混在してもSpeechTranscriberはdiarizationを提供しないため、インポート音声を根拠なく「自分」または「相手」として保存してはならない。

検討した代替案:

- **文字起こしMarkdownのYAML frontmatterを正典にする**: 人間が読みやすく、Obsidianなどで1ファイルとして扱える。一方、Swift標準ライブラリにYAMLパーサがなく、実行時依存の追加または寛容なパーサの自作が必要になる。frontmatterの更新はファイル全体の再書き込みを要し、認識中に確定結果を追記して耐障害性を得る構造とも相性が悪い。外部編集されたYAMLの表現差や破損を、アプリの正典として安全に受け入れる負担も大きいため却下する。
- **JSONLだけを永続的な正典にする**: 確定結果の追記とクラッシュ回復には適するが、認識器由来の不自然な区切りを表示用に統合・分割する操作、手修正、再文字起こし結果の安全な差し替えには向かない。イベント履歴と現在の文書を同じ構造で表現しないため却下する。
- **サイドカーJSONを正典とし、処理中だけJSONLジャーナルを使う**: Swiftの`Codable`を直接利用でき、追加依存がなく、認識中の耐障害性と停止後の整形・更新を分離できる。セッション内のファイル数は増えるが、録音自体が複数ファイルで構成されるため、1ファイル完結の利点はこのレイアウトでは小さい。採用する。
- **SQLiteを正典にする**: 一覧・フィルタ・検索には有利だが、音声ファイルとDBのトランザクション境界、バックアップ、破損回復、外部利用が複雑になる。個人利用の初期規模では必要性が実証されておらず、ファイルとDBのどちらが正かという二重管理も招くため却下する。
- **ファイルを正典、SQLiteをキャッシュにする**: 正典の二重管理は避けられるが、D5で検索方式と規模の閾値を判断する前にキャッシュを導入する理由がない。必要になった時点で追加できるため、S5では導入しない。

## Decision(決定)

1. セッションの永続データはADR-0006のセッションディレクトリ内に置き、停止後の正典を`meta.json`と`transcript.json`の2つのJSONスナップショットとする。Markdownとプレーンテキストは正典から生成する派生エクスポートであり、アプリへ再取り込みして正典を上書きする経路にはしない。
2. `meta.json`はUTF-8 JSONとし、`Codable`で読み書きする。ルートに`schemaVersion`と安定したセッションIDを持たせる。タイトル・開始日時・長さ・タグ・ステータス・ストリーム開始オフセットに加え、ライブ録音かインポートかを示す入力種別と、インポート元の表示名・メディア種別・元の長さなどの来歴を表現できるようにする。各音声トラックにはセッション内で安定したIDと、マイク・システム音声・インポート音声などの由来、表示ラベル、対応する相対ファイルパスを持たせる。具体的なモデルはS5、S10、S19で段階的に定義するが、後方互換な追加と明示的な移行を前提にする。元ファイルの絶対パスは正典にせず、セッション内へ取り込んだ音声を基準にする。
3. `meta.json`の更新は、同じディレクトリの一時ファイルへ完全に書き込み、同期した後に原子的に置換する。更新途中の異常終了では、直前の有効な`meta.json`を残す。S5の新規保存はversion 1とし、既知の開発用version 0は読み込み時にversion 1へ原子的に移行する。未知の新しい`schemaVersion`は破壊的に書き戻さず、非対応として扱う。
4. `transcript.json`は、利用者が現在読む・編集する文字起こし文書のスナップショットとする。ルートに`schemaVersion`、`meta.json`と同じセッションID、独立したリビジョンを持たせ、S5の新規保存はversion 1、既知の開発用version 0は読み込み時にversion 1へ原子的に移行し、未知の新しい`schemaVersion`は破壊的に書き戻さない。認識器の`TranscriptSegment`をそのまま表示単位の正典にはせず、各表示ブロックにトラックID、本文、開始・終了時刻、完了状態を保持する。現在の`TranscriptSegment.stream`はライブ録音のトラックIDへ変換する。インポートした混合音声は専用トラックへ帰属させ、diarizationできない限り表示ラベルを「音声」などの中立な値にして、根拠のない話者属性を付けない。停止後の整形は同じトラックの隣接結果を句読点・無音区間・時刻の重なりなどで統合または分割し、異なるトラックを混ぜず、元の時間範囲を失わない。文章として言い切られていない末尾ブロックも捨てない。
5. 停止後の整形は認識・保存から独立した変換段階とし、MimizukuCoreのSendableな値型を入出力にする差し替え可能な契約の裏へ置く。初期実装は句読点、無音区間、トラック、時間範囲を使う決定的な純ロジックとし、クラッシュ回復や正典の読み書きは整形器の実装に依存させない。将来オンデバイスの自然言語処理やLLMによる整形を追加する場合も同じ契約へ実装を追加し、元のトラック帰属と時間範囲を保持する。音声または文字起こしをデバイス外へ送る実装は、ハード制約と将来のクラウド利用条件を変更する別ADRなしには導入しない。
6. ライブ録音、インポート、再文字起こしの処理中は、1つの`transcript.journal.jsonl`へ確定した認識結果を1行1JSONで到着順に追記する。多数のJSONファイルを作るのではなく、1つのファイルへ複数行を記録する。各認識処理にrun ID、各行にジャーナルのschema versionと単調増加するsequenceを持たせ、各行を改行まで書き、同期が完了した時点で永続化済みとみなす。未知のschema versionを持つ行は解釈または書き換えず、非対応として報告する。volatile結果はライブ表示のためメモリ上に保持し、通常はジャーナルへ書かない。
7. 正常停止ではセッション全体を即時cancelせず、まず音声入力を閉じ、Speechのfinalizeと結果列の完了を最大5秒待つ。最後のvolatile結果が確定結果になればジャーナルへ追記し、その後に整形する。finalizeが失敗または5秒の期限を超えた場合でも、最後に表示されていた文章を黙って捨てず、未完了であることを表現した末尾ブロックとして保存する。
8. 認識終了後はジャーナルから表示ブロックを構築し、`transcript.json`を`meta.json`と同じく原子的に置換する。スナップショットには生成元のrun IDと適用済みsequenceを記録し、新しいスナップショットの同期が完了した後にだけ、対応するジャーナルを削除する。置換後・削除前に異常終了しても、再起動時に同じ行を重複適用しない。異常終了でジャーナルの末尾行だけがJSONとして不完全な場合は、その不正な末尾バイトを文字起こし本文とは区別して無視し、それ以前の完全な行を回復する。途中の行が壊れている場合は黙って欠落させず、破損として報告する。
9. インポートと再文字起こしも同じジャーナルからスナップショットを作る。既存の`transcript.json`は新しい認識と整形が成功するまで変更せず、差し替え確認後に原子的に置換する。手修正済みの文書を黙って上書きしないため、スナップショットにリビジョンと編集状態を持たせる。再文字起こし履歴を恒久保存するかはS18で決める。
10. `meta.json`または`transcript.json`が欠落・破損していても、セッションディレクトリ、録音ファイル、読み取れるジャーナルを削除しない。`SessionStore`はセッションを救済対象として列挙し、セッションID、独立リビジョン、トラック参照を検証した上で、復元可能な最小情報を提示する。修復時も元ファイルを破壊的に上書きしない。
11. `meta.json`と`transcript.json`は別ファイルであり、両方を同じファイルシステムトランザクションでは更新できない。捕捉開始前に初期`meta.json`を同期し、終了時は`transcript.json`を先に同期・置換してから、長さやステータスなどの派生メタデータを更新する。途中で異常終了してmetaが古い状態になっても、有効なtranscriptとジャーナルを失わず、再起動時に派生値を再計算する。セッションIDまたはトラック参照が一致しないファイルは自動的に組み合わせず、救済対象として保持する。
12. SQLiteやFTSを追加する場合はD5で別途判断する。追加する場合も`$XDG_CACHE_HOME/mimizuku/`配下の再構築可能な索引に限定し、`meta.json`と`transcript.json`を正典のまま維持する。
13. AECなどの一時的な診断ログや計測データはセッションメタデータへ混在させない。必要な診断データは、利用者データである本形式とは別の一時的・再生成可能な保存先で扱う。

セッションディレクトリは次の構成になる。

```text
$XDG_DATA_HOME/mimizuku/sessions/<yyyyMMdd-HHmmss>/
  meta.json
  transcript.json
  transcript.journal.jsonl  # 認識処理中・クラッシュ回復時だけ存在
  mic.caf       -> 停止後 mic.m4a
  system.caf    -> 停止後 system.m4a
```

## Consequences(結果)

- (+) Foundationと`Codable`だけで実装でき、MimizukuCoreへYAMLやDBの依存を追加しない。
- (+) 処理中の追記と停止後の文書を分離し、頻繁な確定結果のたびに文書全体を書き直さず、停止後の区切り直し・手修正・差し替えも原子的に行える。
- (+) kill -9などでジャーナル末尾の書き込みが途切れても、それ以前の確定結果と直前の有効なスナップショットを保護できる。
- (+) ライブ録音、インポート、再文字起こしが同じ認識・finalize・整形パイプラインを共有できる。
- (+) 文字起こしを永続的なトラックIDへ帰属させるため、ライブ録音のマイク／システム音声と、話者不明のインポート音声を同じ文書モデルで誤表示なく扱える。
- (+) 整形器の契約と正典を分離するため、純ロジックからオンデバイスの自然言語処理やLLMへ発展させても保存形式と回復経路を変更せずに済む。
- (+) JSON/JSONLは人間も確認でき、外部ツールから構造化データとして利用できる。Markdownが必要な利用者には派生エクスポートを提供できる。
- (+) 将来SQLite索引を追加しても、削除して再構築できるため正典が二重にならない。
- (-) 1セッションが単一文書では完結せず、外部ツールでMarkdownを直接編集してアプリへ反映するワークフローは提供しない。
- (-) メタデータ、整形、手修正の変更ごとにJSONスナップショットの置換が必要になる。ただし録音中の高頻度な更新はジャーナルへ分離するため、S5の規模では許容する。
- (-) ジャーナルからスナップショットへのコミット、末尾行だけを許容する回復規則、原子的置換、スキーマ移行を`SessionStore`で実装・テストする必要がある。
- (-) 2つの正典スナップショットを同時には置換できないため、transcript先行のコミット順序と、古いmetaの派生値を再計算する回復処理が必要になる。
- (-) Speechの正常終了待ちと強制中止を分離し、停止中のUI状態、待機期限、失敗時の未完了ブロックを設計・テストする必要がある。
- (-) 認識器の結果と表示ブロックが別概念になるため、整形規則と時刻範囲の保持を純ロジックとして実装・テストする必要がある。
- (-) 将来の整形器もトラック帰属、時間範囲、未完了末尾を壊さない契約テストを満たす必要がある。
- (-) 現在の`StreamKind`だけでなく永続トラックモデルが必要になり、S5とS19で変換規則を実装する必要がある。
- (-) SQLiteを先送りするため、セッション数や文字起こし量が線形走査の許容範囲を超えた場合はD5で索引導入を再評価する。
