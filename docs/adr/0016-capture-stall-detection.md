# ADR-0016: 捕捉の停止はソース内部で再構築し、回復しなければfail-closedにする

- ステータス: Accepted
- 日付: 2026-08-20
- 関連: #93, #92, #116, ADR-0006, ADR-0014(決定4・5の期限を本ADR 決定11で改訂), `docs/domain-pitfalls.md` #3 / #10 / #14 / #15

## Context(背景)

`AudioSource`契約は「回復不能な捕捉失敗時は無言で止めずthrowする」ことと、「内部再構築でデバイス由来のフォーマットが変わったら初回の基準フォーマットへ変換して流す」ことを求めている。システム音声tapはこれを満たしていたが、マイク捕捉は満たしていなかった。

マイク捕捉は既定入力デバイスを`AVAudioEngine`で読む。録音中に既定入力デバイスが切り替わると、エンジンは停止して`AVAudioEngineConfigurationChange`を出すだけで自動再開しない。この通知はどこからも購読されておらず(変更前のリポジトリ全体でヒット0件)、tapはバッファを出さなくなるだけでストリームはfinishもthrowもしない。結果としてUIは「録音中」のまま音声だけが欠落し続ける。マイク側にはゼロサンプルwatchdogもなく、AECの5秒期限は参照(render)側専用であり、`AecFeedScheduler`は`.active`状態の沈黙に期限を持たないため、どの経路でも検知されない。

同じ穴はシステム音声tapにも残っている。ゼロサンプルwatchdog(`ZeroSampleWatchdog`)はバッファ到着時にしか状態が進まないため、「IOProcが発火しなくなる」形の停止を原理的に検知できない(コード内のコメントもこの限界を認めていた)。AECを通らない「システム音声のみ」モードでは、これが無言ハングに直結する。当初は同じ時間駆動watchdogをtapにも配線したが、実機で誤検知が判明して撤回した(決定7)。tapは無音時に20秒以上コールバックを出さないことがあり、マイクと違って「無出力=異常」が成立しない。

検討した代替案:

- **検知して即fail-closedにする(却下)**: 実装は最小だが、ドック接続やイヤホン抜き差しといった通常運用のデバイス切替で会議録音が毎回終了する。ADR-0014は参照側について「一度途切れたら即時セッション失敗」を明示的に却下しており、同じ論理がマイク側にも当てはまる。システム音声tapが既定出力変更で再構築して継続するのと非対称にもなる。
- **ゼロサンプルwatchdogを流用する(却下)**: `observe`はバッファ到着で進む設計であり、コールバック自体が止まる障害モードを検知できない。マイクはノイズフロアで厳密ゼロにならないため、ゼロ判定自体もマイクには不適(`docs/domain-pitfalls.md` #11)。
- **`kAudioHardwarePropertyDefaultInputDevice`リスナーを併用する(却下)**: 既定入力の切替は`AVAudioEngineConfigurationChange`が拾う範囲に含まれ、3本目の検知経路は重複になる。必要性が実機で判明した時点で追加する。
- **通知購読 + 時間駆動watchdogの2本にする(採用)**: 通知が出る形(デバイス切替)は素早く、通知が出ない形(スリープ復帰、ドライバの死、IOProc停止)は遅くとも確実に拾える。後者は原因を問わないため、`AudioSource`契約の「無言で止めない」を構造的に保証できる。

## Decision(決定)

1. マイク捕捉のエンジン所有・再構築を`MicrophoneSession`へ移し、制御キューに直列化する。システム音声tapの`TapSession`と対称な構造にする。
2. 検知は2本立てとする。主経路は`AVAudioEngineConfigurationChange`の購読、最終防衛線は時間駆動の`CaptureStallWatchdog`(Coreの純ロジック)。ハードウェアプロパティリスナーは追加しない。判定に必要な時刻はすべて引数で受け取り、経過時間の起点の更新まで含めてCore側に置く。App側に残すのは「周期的に時計を読んで問う」副作用だけとし、テストできない分岐をApp層に作らない。
3. 停止検知の経過時間は、スリープ時間を含む連続時計(`ContinuousClock`)で測る。スリープ中に停止する時計では、復帰後に「経過なし」と見えて止まったエンジンを検知できない。
4. 基準フォーマットは初回buildで固定し、再構築後にデバイス由来のフォーマットが変わったら基準へ変換して流す。基準へ変換できないフォーマットは回復とみなさず失敗させる。下流(`AecPump`・`AudioRouter`・録音ファイル)の変換器は最初のバッファのフォーマットで固定されるため、これは契約要件であって最適化ではない。
5. 再構築の上限回数(既定3回)を超えたらストリームをthrowで終える。成否は「buildが返ったか」ではなく**バッファが実際に再開したか**で判定する。
6. 捕捉開始時の失敗は、watchdogのエスカレーションを待たず即時に報告する。再構築で回復する見込みがなく、待つ分だけ原因が分かりにくくなる。
7. システム音声tapには時間駆動の停止検知を**配線しない**。無音時のtapは2分以上コールバックを出さないことがあり(実測: `first buffer (systemAudio): +20595ms`、撤回後の再検証では `+126518ms` = 126.5秒)、「無出力=異常」と扱えない。録音開始から実際に音が鳴るまでの時間は予測できないため、無出力を根拠にセッションを失敗させない。当初は同じwatchdogをtapにも配線したが、実機でシステム音声のみモードのセッションが2回失敗し、ゼロサンプルwatchdogの再構築とも競合してtapのcreate→destroyを3〜6秒間隔で連打した(`docs/domain-pitfalls.md` #15)。tapは従来どおりゼロサンプルwatchdogと既定出力デバイス変更リスナーで回復する。
8. AEC側の扱いは実機の実測で決着した(2026-08-20)。**epochリセットと`AecTimeline`のcapture側閾値の見直しは不要**とする ―― マイク切替後に`aec recovering`から1.5秒で`active`へ復帰し、回り込み抑制も維持された(`capRebase`による再アンカーが機能している)。一方、**再構築区間を同長の無音で埋める件は本ADRのスコープ外として#116へ切り出す**。実測で、切替1回あたりマイクが約1.9秒(マイク単体モード)、両方モードではマイク0.76秒・システム0.39秒の音声が録音から失われ、再構築のたびに累積することが分かった。これは時間軸の問題であり、AECの収束とは別に扱う。
9. HAL呼び出し(`inputNode.outputFormat` / `engine.start()`)は分単位でブロックしうるため(実測129秒、`docs/domain-pitfalls.md` #16)、専用キューへ分離する。状態管理・停止監視・停止・失敗通知はブロックしないキューに置き、**再構築がブロックしている間も上限到達での失敗判定と利用者の停止が進む**ようにする。当初の設計には「再構築は即座に返る」という暗黙の前提があり、実機で破れた。非SendableなエンジンとNotificationCenterのトークンはHAL側のキューから出さない。再構築が進行中の間は新たな再構築を投入せず、watchdogの判定だけを進める。
10. 停止検知は「再構築が進行中か」で扱いを分ける。何も起きていない停止は2→4→8秒のバックオフで3回まで再構築し、上限で失敗させる。**再構築がHAL内でブロックしている間は、試行回数を増やさず、失敗もさせない。** 代わりに「マイクを再接続中…(◯秒)」をメニューバーへ表示し、見切りは利用者の停止操作に委ねる。

    ブロックに期限を置く案は実測で行き詰まった。ブロック時間は20.7 / 25.2 / 60.5 / 123 / 129秒とばらつき、上限が見えない。build開始から20.5秒 / 60.0秒の時点で失敗させたが、その0.2秒後 / 0.17秒後にいずれもbuildが成功して返っている(予算は最後の到着から数えるため、前者は22秒予算での失敗にあたる)(2026-08-20 実機)。**閾値をどこに置いても「わずかな差で、回復するはずのセッションを殺す」が起き続ける。** #93が禁じたのは「無言で止まること」であり、状態を見せて停止を効かせられるなら趣旨は満たせる。代償として、デバイスが本当に死んだ場合は利用者が停止するまで無音のまま待つ。

11. AECの参照期限(ADR-0014 決定4・5の5秒)を**15秒へ改訂する**。ADR-0014自身が「5秒は初期値であり計測結果で再評価する」と留保しており、本改訂はその再評価にあたる。Bluetooth出力への切替を挟むと参照tapの復旧が5秒に間に合わず、マイクの再構築が814msで成功していてもセッションが失敗した(2026-08-20 実機)。復旧中のマイク原音は同長の無音へ置換されるため、期限を延ばしてもシステム音声が正式音源へ混入することはなく、ADR-0014のfail-closedの不変条件は保たれる。代償は無音区間が最大15秒に伸びること。15秒は暫定値であり、実際の復旧所要時間の実測で再評価する。
12. マイク再構築では、**古いエンジンの後始末を待たない**。新しいエンジンを先に作って起動し、成功してから古いエンジンを専用キューへ投げて畳む。自プロセスのprocess tapが既定出力デバイスを掴んでいる間、出力が切り替わると`AVAudioEngine.stop()`が返らなくなるため(実測108秒以上、`docs/domain-pitfalls.md` #17)、待つとマイクの復旧が後始末に引きずられる。一時的に複数のエンジンが並ぶので(後始末が詰まると通常の2つを超えうる)、古い方のtapが出すバッファは世代番号で捨てる。
13. 切り分け用の診断フラグ`-DisableHiddenReferenceTap`を設ける。有効時はマイク単体モードで隠し参照tapを起動せず、**AEC未処理のマイク原音を正式音源へ流す**。これはADR-0014のfail-closed(raw micへフォールバックしない)に対する**唯一の明示的な例外**であり、診断専用とする。ADR-0015と同じ揮発性の起動引数だけで有効化し(`defaults write`では有効にならない)、既定はオフ。有効時は専用の状態(`AecStatus.diagnosticBypass`)として扱い、メニューバーへ「診断用: エコーキャンセル無効(原音を保存中)」、権限診断画面へ警告シンボル付きで「マイク原音をそのまま保存・文字起こしする」旨を表示する。`failed`を流用しない ―― セッションは継続しているため「停止しました」は事実に反する。この例外を設ける理由は、tapの有無でしか切り分けられない障害(pitfalls #17)が実在し、それを特定するのに必要だったため。

## Consequences(結果)

- 得るもの:
  - 録音中のデバイス切替で音声が無言欠落しなくなる。回復できた場合はセッションが継続し、回復できない場合は明示的な失敗として表示される。
  - スリープ復帰後にエンジンが停止していても検知される(#92 の検討事項3が本決定で解消し、#92 は方針決定と実機検証に絞られる)。
  - 判定ロジック(閾値・バックオフ・上限回数・起点の更新)が丸ごとCoreの純ロジックとしてCIで検証できる。TCC・実機に依存しない。App側には時計読みとタイマーだけが残る。
- 失うもの:
  - 再構築の間、音声は欠落する(無音挿入ではなく欠落)。録音ファイルはその分短くなり、システム音声との頭出しがずれうる。ADR-0006の時刻原点(サンプル計数)は保つが、壁時計とのずれは残る。実測では切替1回あたり0.4〜1.9秒失われ、再構築のたびに累積する。両トラックの欠落量が異なるため相対的なずれも広がる。対応は#116(ADR-0017の実測長の無音挿入で解消。ソース側で欠落が起きる事実は変わらず、時間軸の維持は下流の充填が担う)。
  - 停止から失敗までに遅延がある。発火ごとに基準時刻を更新するため、既定値ではマイクが2+4+8+8=22秒(再構築の所要時間を加算)。`ZeroSampleWatchdog`が上限20秒を許容しているのと同じ性質のトレードオフ。
  - 誤検知したときの代償として、これまで無言で継続していたセッションが失敗しうる。この代償が実際に現れたのがtap側で、実測に基づき決定7で配線を撤回した。マイク側は8回のデバイス切替と27分の連続録音で誤発火が観測されていないが、Bluetoothマイクの一時的な途絶に対する初期閾値2秒の妥当性は継続して確認する。
  - `AVAudioEngine`のインスタンスが再構築で入れ替わるため、通知購読を毎回張り替える必要がある。
  - HAL呼び出しがブロックしている間は失敗させないため(決定10)、デバイスが本当に死んだ場合は利用者が停止するまで無音のまま待つ。自動で見切ることはしない。代わりにメニューバーへ状態を出し、停止操作は即座に効くようにしてある ―― #93が禁じたのは「無言で止まること」であり、その趣旨は状態表示と停止の即応で満たす。
  - AECを通らない「システム音声のみ」モードには、引き続き停止検知が存在しない(決定7)。この穴の扱いは#92で、無音時の無出力ギャップ分布を実測してから決める。
- 維持する保証:
  - ADR-0014のfail-closed(AEC処理済みマイクだけを正式音源とし、raw micへフォールバックしない)は、通常経路では変更しない。本決定はソース側の回復であり、AECの状態機械には介入しない。
  - `AudioSource`契約(cold・単一消費者・nativeフォーマット・ストリーム生涯でフォーマット固定)は変更しない。契約が求める「回復不能な捕捉失敗はthrowする」について、**HAL呼び出しのブロックは回復不能な失敗として扱わない** ―― 実測でブロックは解けて回復するため(pitfalls #17)。この間もストリームは生きたままで、状態表示と停止操作で無言化を防ぐ。
  - 実機・TCC依存の検証は人間がローカルで行う(`docs/domain-pitfalls.md` #8)。CIで検証したと主張するのは純ロジック部分のみ。
