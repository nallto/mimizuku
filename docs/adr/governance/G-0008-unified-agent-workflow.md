# G-0008: Agent作業を単一ワークフローと利用者指定の停止条件に分離する

- ステータス: Accepted
- 日付: 2026-07-29
- 関連: #86, G-0001, G-0004(本ADRで置換), G-0006

## Context(背景)

G-0004ではAgentの作業をApproval-driven、Goal-driven、Budget-drivenに分類し、Issue着手時に利用者へ選択を求めた。しかし実際の運用では、どの分類を選んでも、非自明な変更の計画承認、検証、コミット前確認、PRマージとブランチ削除の承認という必要な停止点は変わらなかった。

分類のための質問と条件分岐は利用者の体験を改善せず、Agentごとの解釈差と文書・skillの重複だけを増やした。完了条件、時間、試行回数などの指定は有用だが、作業手順を切り替える分類ではなく、個々のタスクの停止条件として直接扱える。

検討した代替案:

- **3分類を維持し、説明だけ短くする(却下)**: 選択結果が停止点を変えないため、質問自体の価値がない。
- **分類ごとに停止点を実際に変える(却下)**: 検証や不可逆操作の承認を省く経路が生まれ、G-0001とAgent共通ワークフローの保証を弱める。
- **分類を廃止し、単一ワークフローへ統一する(採用)**: 安全性と実際の体験を維持しながら、不要な質問と分岐をなくせる。

## Decision(決定)

1. Issue着手時にAgentの実行モードを選択・確認しない。リポジトリ固有のApproval-driven、Goal-driven、Budget-drivenという分類を廃止する。
2. すべての作業で、非自明な変更は計画を提示して承認後に実行し、`just check`と必要なverifier検証を通す。未コミットのdiffと検証結果を示して変更確認を受けてからコミットする。
3. PRマージ、ブランチ削除、外部公開などの不可逆・外向き操作は、直前に対象と最新状態を示して明示承認を得る。利用者が完了条件や上限を指定しても、この停止点を省略しない。
4. 利用者が指定する完了条件、時間、試行回数、トークン上限はタスク固有の停止条件として直接扱う。分類名へ変換せず、指定された条件と通常の安全停止点を併用する。
5. TCCや実音声ハードウェアなどCIで検証できない受け入れ条件は、従来どおり人間の実機確認として明示する。自動化の有無を理由に検証済みとみなさない。

## Consequences(結果)

- 得るもの:
  - Issue着手時の不要な選択質問がなくなり、利用者が得る実際の作業体験と規約が一致する。
  - Agent、共通skill、統合手順が一つの停止点モデルを共有し、条件分岐による解釈差がなくなる。
  - 完了条件や予算は、分類を介さず利用者の指定どおり扱える。
- 失うもの:
  - Agent製品が提供する自動実行機能を、リポジトリ固有の名称で案内する表はなくなる。
  - 過去の分類を前提にした会話や外部資料は、G-0008以降の単一ワークフローへ読み替える必要がある。
- 維持する保証:
  - G-0001のPR統合手順、`just check`とverifier、コミット前確認、不可逆・外向き操作の承認は変わらない。
  - 音声・TCC・ハードウェア依存の確認は人間が実機で行う。
