# G-0013: テストカバレッジ駆動の改善ループを有限バックログ + CI floorで運用する

- ステータス: Accepted
- 日付: 2026-08-29
- 関連: #129(親Issue)/ #125(patrol)/ G-0010(無人実行の境界)/ G-0012(本ADRの計画は設計レビュー round 0〜5 を通過。記録は #129 コメント)

## Context(背景)

#129 は、MimizukuCore のテストカバレッジを駆動目標(set point)とする改善ループを patrol の巡回項目として設計することを求めている。実測ベースライン(2026-08-29、ローカル: lines 93.91% / regions 88.33% / functions 92.58%、テスト179件)では未カバーが `SessionStore+Recovery.swift`・`AacConverter.swift` の復旧・変換失敗系エラーパスへ偏在しており、量は有限である。一方でリポジトリのテスト方針は「カバレッジ数値を動かすことだけを目的としたテスト(アサーションなし・実装をなぞるだけ)」を禁止しており、恒久的に数値を上げ続けるループはこの規約への圧力になる。決めるべきは、(1) 計測スコープ、(2) 停止条件の正典(set point)、(3) 無人実行の境界内での駆動方法、(4) 退行防止(CI floor)の定義と置き場所である。

検討した代替案: (a) 恒久の「毎回少しずつ上げる」ループ ―― 正当な仕事が尽きた後にカバレッジ稼ぎテストを書く圧力になるため却下(#129 本文の方針どおり)。(b) 数値目標(例: 95%)を set point にする ―― 数値目標そのものが稼ぎテスト圧力になり、「終わり」も定義できないため却下。(c) wont-cover 台帳なしの「未カバー一覧ゼロ」 ―― 「テスト価値なし」と判断される未カバーの受け皿が無いと set point が事実上「全 region を必ずテストする」強制となり、稼ぎテスト禁止の規約と矛盾するため却下(現時点で具体的な wont-cover 対象は未確定であり、台帳は空から始める)。(d) region 単位の台帳識別子 ―― llvm-cov の region はコード変更で振り直され安定識別子にならないため却下(関数単位+実測紐づけ失効を採用)。(e) coverage floor を `just check` へ統合(案A) ―― 「just check = CI」の文言を守れるが、全開発者の毎回の検証にカバレッジ計測ビルドが乗るため却下(人間裁定)。(f) coverage の required check 即時昇格 ―― floor の安定稼働を確認する前は時期尚早のため却下。

## Decision(決定)

1. **計測スコープは positive inclusion で固定する。** 集計対象は `Packages/MimizukuCore/Sources/MimizukuCore/` 配下のソースに限定し、llvm-cov へ対象ソースパスを明示指定する(除外 regex 方式は採らない)。テストバイナリへ将来別ターゲット(AecDiagCLI 等)のソースがリンクされても集計へ混入しない。MimizukuCore パッケージへ新しい library ターゲットを追加する場合、スコープへ入れるかは本 ADR の改訂で明示更新するまで対象外。App/ ターゲット(xcodebuild 別 job、`swift test` 対象外)はスコープ外。スコープに一致するソースが 0 件になった計測は fail とする(空集合の vacuous pass を許さない)。
2. **set point(停止条件の正典)は sensor 出力ゼロとする。** sensor 出力 = 「スコープ内の未カバー region 一覧 − wont-cover 台帳の有効項目」。数値目標は置かない。Issue #129 本文の「未カバー一覧ゼロ」との差異(wont-cover 控除後のゼロ)を明示する。
3. **wont-cover 台帳はリポジトリ内の sensor 設定ファイルを正典とする**(PR2 で導入、空から開始)。項目はファイル+シンボル(関数)単位で、1 件ごとに理由必須。シンボルは完全修飾名+型署名で一意に識別し、曖昧(同名・オーバーロード)・解決不能・存在しないシンボル(stale)・schema 違反(理由の欠落・不正・同一シンボルの重複行)はすべて sensor がエラーにする(fail-closed)。項目は登録時の実測に紐づける: 登録時に対象関数の region 総数と未カバー region 数を記録し、sensor は毎計測で現在実測と照合して、どちらか一方でも不一致なら項目を失効させ、その関数の未カバーを sensor 出力へ戻す ―― 実装変更(region 構成の変化)もテスト集合の変化(テスト削除・弱体化によるカバー減)も同じ規則で機械検出される(llvm-cov からの取得実装は PR2)。台帳の追加・削除は人間承認の PR のみとし、無人実行では変更しない。
4. **駆動は patrol の巡回項目として、sensor 計測+提案までとする**(G-0010 決定6)。提案の経路は report-queue と Issue コメントのみ(無人での Issue コメント記録は、無人境界の正典 `docs/development.md`「無人実行と報告キュー」の許可行「docs・ADR・Issueへの記録」に基づく。なお G-0010 決定4 の字義「pushとdraft PRに限る」とこの許可行には文言乖離が実在するため、整合提案を別 Issue として起票する)。draft PR は作らない ―― テストコード・雛形を無人で書くことは「新たな非自明な変更への着手」に該当する(Issue #129 本文の「提案(report-queue / draft PR)」からの意図的な縮小)。テスト追加の着手は人間の承認後。計測は毎巡回でなくてよい(coverage 計測は他項目より桁違いに重い)― 低頻度化を許し、具体頻度と patrol SKILL.md の停止条件記述は PR3 で確定する。
5. **目標到達後も patrol 項目は残して継続監視する。** sensor 出力ゼロの間は提案なし(計測と確認のみ)。コード変更や台帳失効で新規未カバーが現れれば提案が自動で再開する。「駆動ループの停止」とは提案対象が無い状態を指し、計測の停止ではない。
6. **CI coverage floor は lines % の整数切り下げで定義する**(ツールチェーン差の偽 red をバッファで吸収)。初期 floor は「PR4 導入時の CI ランナー上の実測」の整数切り下げとする(ローカル実測ではない。起票時点のローカル実測では 93%)。取得手順: coverage 計測 step はマージ前の main に存在しないため、PR4 ブランチ上の CI 実測で代用する ―― 前提として PR4 は Swift ソース・テストへ一切触れず(justfile・ci.yml・文言ファイルのみ)、かつ floor の確定は最新 main を取り込んだマージ直前の head の CI 実測で行う(マージ承認時に main 追従済みであることを確認する)。実測が整数境界の直上でバッファが過小な場合は複数 run で実行間分散を確認してから決める。floor は ratchet(上げのみ)で、バックログ消化の進行に応じ実測切り下げ値へ上げる PR を人間承認で入れる。無人実行は floor 変更 PR を作らない。
7. **floor の置き場所は独立レシピ + CI 追加 step とする**(案B)。`just coverage-floor` を justfile へ置き、CI の check job が `just check` の後の追加 step として実行する。ローカルでも同一コマンドで再現できる(2 コマンドになる)。「just check = CI と同一内容」系の文言は「CI の check job が実行する検査はローカルの just レシピ(`just check` + `just coverage-floor`)で同一に再現できる」へ PR4 で改訂する。対象: AGENTS.md「検証(最重要ルール)」、justfile 冒頭コメントと check レシピコメント、`scripts/setup-check.sh` 冒頭コメント、README.md、CONTRIBUTING.md、`docs/development.md`、`docs/architecture.md`、`.github/workflows/ci.yml` 冒頭コメント、`.agents/skills/check/SKILL.md` と `.claude/skills/check/SKILL.md` の description(後2者により PR4 は `.agents/`・`.claude/` へ触れるため agent-config 影響表を要する)。app-build job と docs workflow はこの文言の対象外 ―― 対比説明を書く場合、app-build は署名条件が異なる(CI は未署名・ローカルは通常署名)ため「同一に再現」とは書かない。Accepted 済み ADR の歴史的記述は変更しない。
8. **floor は fail-closed とする。** 実測が floor 未満なら原因を問わず red(ツールチェーン差・ランナー更新・マージスキュー起因を含む)。計測ツールの失敗(profdata 欠損等)・スコープ一致 0 件も red(検査不成立を pass にしない)。復旧経路は 2 系統を区別する: 実測を floor 以上へ戻す修正 PR(テストの追加・復元)は本ループの主経路であり通常運用。floor 側の復旧(引き下げ・再設定)は本 ADR の改訂のみで行い、通常 PR では行わない。
9. **カバレッジ稼ぎテストの判断基準をレビューの正典とする。** アサーションのないテスト、実装をなぞるだけのテスト、境界値・異常系の意図説明ができないカバレッジ目的のみのテストはレビューで拒否する。floor はこの圧力を構造的に持つが、機械では区別できない ―― 抑止はレビューであり、本基準を判断の根拠にする。
10. **required check 化は floor の安定稼働を確認してから PR4 以降で判断する**(旧ブロッカー #131 は CLOSED 済み)。

## Consequences(結果)

- 得るもの: 「終わり」が機械判定できる有限バックログ(sensor 出力ゼロ)と、それ以後の退行防止(floor)。数値目標を持たないことで稼ぎテスト圧力を構造的に避け、wont-cover の明示分類で「テストしない」判断が理由つきで記録される。コード変更もテスト削除も同じ失効規則で sensor 出力へ戻るため、退行が黙って隠れない。
- 失うもの: 進捗を単一の「%」で読めない。台帳・失効照合・floor の実装(PR2〜4)と、CI check job の実行時間増(カバレッジ計測ビルド)。「just check = CI」の文言改訂(対象10箇所)。
- 規律で残る部分(機械強制できない): 稼ぎテストの混入と wont-cover 理由の形骸化はレビューでのみ抑止される。台帳失効の縁(変更後も region 総数と未カバー数が偶然一致するケース)は機械検出されない。マージスキュー(並行 PR が各自の head で floor を通過し統合後の main だけが割れる)は main push の CI で初めて red になる ―― 復旧はカバレッジを戻す通常 PR。
- 成立しなくなる条件: llvm-cov の出力形式・region 意味論が大きく変わった場合、または MimizukuCore のパッケージ構成が複数 library へ分割された場合は、スコープと台帳形式を本 ADR を書き換えず新しい ADR で改訂する。
