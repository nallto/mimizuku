# ドメインの落とし穴

現実の報告で検証済み。再発見しないこと。AGENTS.md(ハード制約)と計画から参照される。捕捉・文字起こしのコードに触れる前に再読する。

## Core Audio process taps(システム音声捕捉、macOS 14.2+ API)

- **#1 排他フラグの反転。** `CATapDescription(stereoGlobalTapButExcludeProcesses:)` は排他性を自動設定する。後から `isExclusive` を変更すると意味が反転し(「列挙 PID 以外すべて」→「列挙 PID のみ」)、無音になる。このイニシャライザの後で `isExclusive` に触らない。
- **#2 AVAudioEngine を tap 付き aggregate device に向け直せない。** デバイス設定は `noErr` を返すが、エンジンは既定入力を読み続ける。aggregate は `AudioDeviceCreateIOProcIDWithBlock`で直接消費する ―― AVAudioEngine ではない。
- **#3 長時間セッションのゼロサンプル劣化。** IOProc は正常に発火し続けるのに、サンプルがすべて厳密に `0.0f` になることがある。回復には process tap と aggregate device の**両方**を破棄・再作成する必要がある。IOProc の再起動だけでは直らない。`AudioSource` 実装はこれを検知して**ソース内部で**両方を破棄・再作成し、ストリームは切らずに継続する(S3 のゼロサンプル watchdog)。正当な無音と劣化はソースから区別できないため、発火間隔はバックオフさせ、無音だけではセッションを殺さない(`ZeroSampleWatchdog`)。
- **#4 TCC プロンプトは署名済みバイナリでのみ出る。** `NSAudioCaptureUsageDescription` のプロンプトは正しく署名されたビルドでのみ表示される。未署名 / ad-hoc デバッグビルドでは無言で何も録れないことがある。「音が録れない」の調査前に署名を確認する。

## SpeechAnalyzer / SpeechTranscriber(macOS 26+)

- **#5 モデルアセットはロケール単位で大きい。** 数百 MB。初回利用前に `AssetInventory` で導入を保証する必要がある。オンデマンドではなくアプリ起動時にバックグラウンドでダウンロードし、初回利用がダウンロードでブロックしないようにする。
- **#6 volatile と final。** `.volatileResults` は暫定セグメントを生み、後で確定版に置き換わる。確定セグメントのみwrite-throughジャーナルへ永続化し、volatileは薄く(dimmed)描画する。利用者の停止でセッションTask全体を即時cancelすると最後のvolatileが確定する機会を失うため、入力ストリームだけを正常終了させて`finalizeAndFinishThroughEndOfInput()`と結果列の完了を待つ。5秒を超えた場合だけTaskをcancelし、メモリ上の最後のvolatileを未完了末尾としてスナップショットへ残す(#38)。
- **#11 完全無音の入力から幻聴セグメントが出る。** 厳密ゼロのバッファ(システム音声 tap の無音)を供給し続けると、SpeechTranscriber が短い幻聴セグメント(「あ」1 文字等)を確定として生成することがある(S3 実装時に実機で観測、再現性あり)。厳密ゼロのバッファは解析へ供給しない。ただし単純にスキップすると解析タイムラインが圧縮されて `audioTimeRange` が録音とずれるため、**全バッファに `AnalyzerInput(buffer:bufferStartTime:)` で開始時刻を明示**して供給する。マイクはノイズフロアで厳密ゼロにならないため影響しない。さらに、スキップしたままだと認識器が発話終端の無音を観測できず **volatile が確定しないまま残る**(動画停止 = 完全無音で灰色行が残り続ける。#63 実機で観測)。ゼロ連続が閾値(1 秒)を超えたら `SpeechAnalyzer.finalize(through:)` で保留結果を明示的に確定させる。

- **#7 話者 diarization は無い(ただしマイク / システムの区別は保持される)。** 2 階層を分けて考える。(1) ストリーム同一性 ―― 音声がマイク由来かシステム音声 tap 由来かは常に判別可能で、`TranscriptSegment.stream`(`.microphone` / `.systemAudio`)に必ず載る。「自分 vs 相手」の振り分けや、並列表示・チャット形式表示はこの 1 フィールドで実現できる(将来チャット形式にしても、どちらのストリーム由来かは失われない)。(2) diarization ―― 1 つのストリーム内で複数話者を区別する機能は無い(例: システム音声に相手 A・B・C が混在していても分離できない)。UI や docs では「自分 / 相手」までは表明してよいが、相手側の話者分離は主張しない。

## AVAudioEngine(マイク捕捉)

- **#10 捕捉開始前の `inputNode.outputFormat(forBus:)` 事前照会はクラッシュしうる。** 使い捨ての `AVAudioEngine()` を作って init 時(MainActor 上)にフォーマットを先取りしたところ、`AVAudioIONodeImpl::GetOutputFormat` 内でクラッシュした(S2 実装時に実機で観測)。ハードウェア照会は `buffers()` 内で実際に使うエンジンに対してのみ行い、下流(録音ファイル・変換器)は**最初のバッファの `format` から遅延確定**させる(`AudioFileWriter` の遅延オープン、`AudioRouter` の遅延変換器生成)。HAL への同期照会は main thread では行わない。

- **#14 既定入力デバイスが録音中に切り替わると、マイク捕捉は無言で止まる。** `AVAudioEngine` は稼働中に既定入力デバイスが切り替わると停止し、`AVAudioEngineConfigurationChange` を出すだけで自動再開しない。購読しなければ tap はバッファを出さなくなるだけで、`AsyncThrowingStream` は finish も throw もしない(下流の `for await` が永久待機する)。ゼロサンプル watchdog(#3)はバッファ到着時にしか状態が進まないため、この障害モード ―― コールバック自体が来なくなる ―― を原理的に検知できない。マイクはノイズフロアで厳密ゼロにならないため、ゼロ判定自体もマイクには使えない(#11)。対策は**通知購読による再構築 + 時間駆動 watchdog(`CaptureStallWatchdog`)の 2 本立て**で、経過時間はスリープ時間を含む連続時計で測る(スリープ中に止まる時計だと、復帰後に「経過なし」と見えて止まったエンジンを検知できない)。決定は ADR-0016。

  - **通知が飛ばないデバイス変更が実在する(実機で確認)。** 24kHz のマイクから 48kHz のマイクへ切り替わった際、`AVAudioEngineConfigurationChange` が一度も配信されず、時間駆動 watchdog だけが停止を検知して復旧した。**通知 1 本の実装では不十分**で、最終防衛線が要る。
  - **復旧に要する時間(実測)。** 通知経路では検知から再開までの欠落が 51〜111ms(初回のみ 461ms)。watchdog 経路では検知に閾値ぶん(既定 2 秒)かかり、再構築自体にも 1.65 秒を要した。
  - **通知の購読先はエンジンインスタンスに縛られる。** `object:` に渡したエンジンが再構築で差し替わると、古い購読は二度と配信されない。購読の張り替えは build / teardown に寄せ、再構築の経路(通知・watchdog)によって不変条件が変わらないようにする。
  - **出力デバイスの変更でも入力エンジンへ通知が飛ぶ(実機で確認)。** 既定出力を変えるとマイクが再構築される。害はないが、入力を触っていないのに再構築が走って見える。
  - **基準フォーマットはセッション開始時のデバイスで固定される。** 24kHz の Bluetooth マイクで開始したセッションは、途中で 48kHz のマイクへ替えても最後まで 24kHz で記録される(`AudioSource` 契約により、録音ファイル・AEC・変換器が最初のバッファのフォーマットで固定されるため)。仕様どおりだが利用者には意外な結果になりうる。

- **#15 システム音声 tap は「無出力 = 異常」ではない。無音時は 20 秒以上コールバックが来ないことがある。** #14 と同じ時間駆動 watchdog を tap にも配線したところ、**システム音声のみモードで何も再生せずに開始したセッションが、3 回の再構築の末に失敗した**(実機で 2 回再現)。同じログに `first buffer (systemAudio): +20595ms` が出ており、最初のバッファまで **20.6 秒**かかっていた。撤回後の再検証では、システム音声のみモードで何も再生せずに開始したところ **`first buffer (systemAudio): +126518ms`(126.5 秒)** を観測している。無出力の上限は少なくとも 2 分を超えるため、閾値を延ばして救う方向は成立しない。**録音開始から実際に音が鳴るまでの時間は予測できない**ため、tap の無出力を根拠にセッションを失敗させてはいけない。さらにこの再構築要求はゼロサンプル watchdog の再構築と競合し、3〜6 秒間隔で tap の create→destroy を連打する状態になった(#3 / #13 が tap を壊すと警告しているパターン)。`ZeroSampleWatchdog` が 5 秒 → 20 秒のバックオフを持つ理由(正当な無音と劣化を区別できない)がそのまま当てはまる。**tap 側に時間駆動の停止検知は入れない**(ADR-0016 決定7)。結果として「IOProc が戻らない形の停止」は現状どの watchdog も拾えず、AEC を通らないシステム音声のみモードには期限が存在しない ―― この穴の扱いは #92 で、無音時の無出力ギャップ分布を実測してから決める。

- **#12 voice processing(VPIO の AEC)はシステム音声 tap と両立しない。** スピーカー再生音がマイクへ回り込む(「自分」として二重に文字起こしされる)対策に`inputNode.setVoiceProcessingEnabled(true)` を試したところ、次の 2 つが実機で判明した(S4)。(1) VPIO は**システム全体で他アプリ音声をダッキング**し、`voiceProcessingOtherAudioDuckingConfiguration` を `.min` にしても process tap の捕捉信号が約 20dB 減衰する(耳には「少し小さい」程度でも文字起こしには実質無音 ―― tap はダッキング後の信号を拾う)。FaceTime 等が AEC と相手音声を両立できるのは相手音声を自分の VPIO 出力から再生しているためで、他アプリの音を tap で拾う本アプリでは同じ手が使えない。(2) VPIO 有効化で入力フォーマットが多チャンネル化することがある(実測: 5ch Int16 discrete・全チャンネルがビット同一の複製。5ch discrete の CAF は AAC 変換できない)。結論: **VPIO の AEC は採用しない**。回り込み対策は **ソフトウェア AEC(WebRTC AEC3)を自前の同期層越しに適用**する方式へ移行した(ADR-0013、#59 で解決)。VPIO と違いシステム音声 tap をダッキングしないため両立する。

- **#13 マイク単体モードの AEC は「隠しシステム音声 tap」を要し、システム音声 TCC と結合する(AEC-4 / #64 / ADR-0014)。** WebRTC AEC3 は near-end(マイク)を消すために far-end 参照(スピーカー出力 = システム音声)を必要とする。そのため「マイクのみ」モードでも回り込みを消すには、録音・文字起こしに出さない参照専用の system tap を裏で起動する。帰結として、**マイク単体モードの初回起動でシステム音声の TCC プロンプトが出る**(ユーザーがマイクだけ選んでいてもシステム音声許可を求められる ―― 用途説明でカバー)。マイク原音にはシステム音声が回り込み得るため、参照 tap が使えない場合に原音へフォールバックしてはいけない。初回 render 前と復旧中は原音を同長の無音へ置換し、期限内に開始・復旧できなければセッションを失敗させる(当初5秒。Bluetooth出力への切替で足りず、ADR-0016 決定11で15秒へ改訂)。診断表示は「参照待ち / 有効 / 復旧中 / 失敗」とする(#76)。

  - **参照 tap の直前に process tap を事前プローブしてはいけない(実機で回り込みが残った)。** 可用性判定のつもりで `SystemAudioProbe`(`AudioHardwareCreateProcessTap` → 即 `Destroy`)を挟むと、その直後に作る本番の参照 tap が**無音になり AEC が何も打ち消せない**(診断は「有効」表示のまま回り込みが「自分」に混入する)。両方モードには事前プローブが無く打ち消せている ―― これが唯一の構造差だった。参照 tap は遅延ソースの中で**直接起動**し、両方モードと同一経路(本番 tap を直接消費)に揃える(create→destroy→create の連続が tap を壊す。#3 のゼロサンプル系と同根)。
  - **参照未着のcaptureを保留し続けたり、原音bypassで救済してはいけない。** 保留は参照沈黙時に全損・恒久遅延を招き、原音bypassはシステム音声を正式なマイク音源へ混入させる。初回render前のcaptureは即時に同長の無音へ置換して時間軸だけを維持し、到着と独立したwatchdogで期限後に開始失敗させる。終了時drainはwatchdogと別APIにし、状態遷移や失敗通知を発生させない(#74 / #76)。
  - **初回 render 到着後に、参照開始前の capture を APM へ遡及投入してはいけない。** 両方モードはマイク側ルーターが先に起動し、system tap が約 +1.2 秒遅れることがある。対応参照のないnear-endを先にAPMへ流すと初期収束を崩す。開始前captureは原音を無音へ置換し、参照開始後のcaptureからAECを開始する。actorへの到着順は入れ替わるため、初回renderのhost timeより古いcaptureも同様に無音化する。診断の「有効」は最初のcaptureを実際にAPMへ入れた後に表示する(#76)。
  - **render一時停止時に無音参照でcaptureをAPMへ通し続けてはいけない。** 形式上は処理済みでもAECが打ち消せない原音相当になり得る。対応renderを200ms待っても得られなければrecoveringへ移り、マイク原音を同長の無音へ置換する。renderが戻ったらAPM・aligner・render framerを新しい同期epochへリセットし、期限内に戻らなければセッションを失敗させる。capture framerはリセットせず、復旧境界を跨ぐフレームをhost timeで無音化して10ms未満の欠落も避ける。隠し参照tapのストリーム終了は500ms backoffで新しいtapを生成して復旧を試す(#76)。
  - **system tap がマイクより「先に」起動すると、先行 render が貯まって AEC3 が打ち消せない(両方モードでも起動順で発生。実機で確認)。** 通常は tap がマイクの +1.2 秒後に起動するが、起動順は環境で入れ替わる。tap 先行だとマイク到着までに render が貯まり、最初の capture 供給時に**貯まった全 render を一気に APM へ流す** → AEC3 から見た far-end↔near-end 遅延が探索窓を超え、エコー遅延を推定できず**打ち消せない**(テレメトリ上は同期健全:filled=0・droppedRender=0 なのに実機で回り込みが残る。録音の回帰係数 α で 0.34 = 漏れ、マイク先行時は 0.02〜0.08)。`AecAligner.maxRenderLead`(既定 0.25 秒)で **capture より先行しすぎる render を APM に流さず捨て**、先行量を AEC3 の窓内に抑える(既存の「render 未開始まで capture を流さない」= capture 先行対策の**対称版**。診断は `aec finished` の `leadDropped` に出る)。

- **#16 `AVAudioEngine` の起動と `inputNode.outputFormat` は分単位でブロックする。** 入力デバイスが不安定なとき(USB マイク → AirPods → USB マイクのような連続切替の最中)、`outputFormat(forBus:)` と `engine.start()` が**返ってこない**。実測で 25.2 秒、123 秒、129 秒のブロックを観測し、25 秒のケースは最終的に `com.apple.coreaudio.avfaudio error 35` で失敗した(2026-08-20、#93 の実機検証)。**再構築が即座に返る前提でコードを書いてはいけない。**
  - 帰結として、再構築と同じキューに監視や停止処理を置くと、**ブロック中は停止検知のエスカレーションも利用者の停止操作も進まない** ―― fail-closed の保証が、それが必要な場面でちょうど失われる。実測ログでは、利用者が停止操作をしてから実際に停止するまで 2 分かかっていた(build が返った直後にキューへ溜まっていた stop が実行された)。
  - この間エンジンは破棄済みで再作成はブロック中なので、**メニューバーのマイク使用インジケータが消え、文字起こしも止まる**。UI は「録音中」のままになる。
  - **ブロック時間に上限を置く対策は成立しない(実測)。** 20.7 / 25.2 / 60.5 / 123 / 129 秒とばらつき、上限が見えない。build 開始から 20.5 秒 / 60.0 秒の時点で失敗させたが、その 0.2 秒後 / 0.17 秒後にいずれも build が成功して返った(予算は最後の到着から数えるため、前者は 22 秒予算での失敗にあたる)。閾値をどこに置いても「わずかな差で、回復するはずのセッションを殺す」が起き続ける。**ブロックを理由に失敗させず、状態を利用者へ見せる**(ADR-0016 決定10)。
  - `engine.start()` が成功を返しても、その直後からバッファが 1 つも流れないことがある(実測: start 成功の 2.1 秒後に stall 検知)。**「start が返った = 捕捉が動いている」ではない。**
  - 対策: HAL 呼び出し専用のキューを分け、状態管理・停止監視・停止・失敗通知はブロックしないキューに置く(ADR-0016 決定9)。`AVAudioEngine` の同期 API にタイムアウトは無いため、キュー分離が実質唯一の手段。非 Sendable な `AVAudioEngine` と通知トークンは HAL 側のキューから出さない。

- **#17 自プロセスの process tap が生きている間、既定出力デバイスが切り替わると `AVAudioEngine.stop()` が返らなくなる。** マイク捕捉の再構築が「古いエンジンの破棄」で止まり、実測で 108 秒以上ブロックした。**出力デバイスに実際に音が流れると即座に解ける**(動画を再生すると、その瞬間にマイクが復旧する。複数回再現)。切り分けは実機の 2 実験で確定した(2026-08-20、#93)。
  - 実験1: build を「破棄 / フォーマット照会 / 起動」の 3 段階でログしたところ、**破棄の段階**で止まっていた。起動ではない。
  - 実験2: 隠し参照 tap(マイク単体モードの far-end 参照。#13)を起動引数で無効化すると、**まったく再現しない**。
  - つまり「自分の tap が、自分のマイクを止められなくしている」。tap の private aggregate device は既定出力デバイスを主サブデバイスに持つ(#2)ため、出力デバイスの切替中は HAL 側の後始末が完了せず、同じプロセスの `AVAudioEngine.stop()` がそれを待つ形になる。
  - 対策: **古いエンジンの後始末を待たない。** 新しいエンジンを先に作って起動し、成功してから古いエンジンを専用キューへ投げて畳む(ADR-0016 決定12)。一時的に 2 つのエンジンが並ぶため、古い方の tap が出すバッファは世代番号で捨てる。
  - **対策後もブロックは消えず、照会側へ移った(実測)。** 後始末を待たなくすると大半の再構築は 87〜173ms で完了するが、`inputNode.outputFormat(forBus:)` が 14.7 秒ブロックする例が残る。同じ根(出力デバイス切替中に入力側の HAL 操作が詰まる)なので、後始末だけの問題ではない。残りの経路は #113 で扱う。
  - 切り分けには診断用の起動引数 `-DisableHiddenReferenceTap YES` が使える(揮発性・既定オフ)。隠し参照 tap を起動せずマイク原音を流すため **AEC は効かない**。実験専用。
  - 注意: マイクのみを使うつもりでも、AEC のために隠し参照 tap が動いている(#13)。「システム音声を使っていないから tap は関係ない」は成立しない。

- **#18 AirPods(HFP)が既定出力の間、システム音声 tap は実時間の約半分のサンプルしか出さない(申告フォーマットは 48kHz のまま)。** AirPods をマイクとして使うと出力も HFP モード(実効約 24kHz)になるが、tap は `48000Hz 2ch` を申告し続け、実際に届くサンプル数は実時間の約半分になる。結果は**2 倍速の早送り + 半分の欠落**(実機の聴感: 1 秒の音声が 0.5 秒で再生され 0.5 秒の空白が続く)。#116 の欠落充填はこの不足を毎回実測して無音で埋めるため時間軸は保たれるが、内容の早送りは残る(充填が可視化するまで、この現象は「録音が無言で短くなる」形で隠れていた)。裏取りは 3 系統が一致: 充填ログが AirPods 出力期間に限り 2:1 の周期で発火(USB/内蔵期間はゼロ)、独立実装の `AecAligner` 内部充填(`filled`)が同じ欠落量を 0.01 秒単位で一致計測、AEC の render ドリフト実測 −17〜−24%(2026-08-20、#119)。対策(実効レートの検出と解釈し直し)は #119 で扱う。AEC の far-end 参照も同じ歪んだ信号を受けるため、この期間の回り込み抑制は信用しない。

## CI

- **#8 ホスト型ランナーは TCC 権限を付与できない。** マイクやシステム音声 tap に触れるものはすべてローカル限定。CI は `macos-26` ランナーで純ロジックのパッケージテストを実行する。音声/権限挙動を「CI で検証した」という主張は定義上偽 ―― 代わりにローカル実行ログを要求する。

## Swift 6 concurrency

- **#9 `AVAudioPCMBuffer` は `Sendable` ではない。** アクター/ストリーム境界を跨ぐと、明示的なコピーか `sending` の判断が必要になる。実装時に明示的に解決し、正当化理由を書かずに`@unchecked Sendable` で覆い隠さない(ハード制約 #4)。
